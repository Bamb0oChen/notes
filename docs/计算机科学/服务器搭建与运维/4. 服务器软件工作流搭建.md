## 三、逐层展开

### 3.1 容器技术基础层

#### 3.1.1 容器 vs 虚拟机的本质区别

这是理解现代服务器软件部署方式的基石。

| 维度 | 虚拟机 (VM) | 容器 (Container) |
|------|-------------|------------------|
| **内核** | 每个 VM 有独立的 Guest OS 内核 | 所有容器共享 Host OS 内核 |
| **启动时间** | 分钟级（需引导整个操作系统） | 秒级（进程级启动） |
| **资源占用** | GB 级（完整的操作系统） | MB 级（仅应用及其依赖） |
| **隔离级别** | 硬件虚拟化，强隔离 | Namespace + Cgroup，进程级隔离 |
| **迁移成本** | 高（需要迁移整个 VM 镜像） | 低（容器镜像可移植） |
| **典型代表** | VMware、VirtualBox、KVM | Docker、Podman、containerd |

**关键理解**：容器不是「轻量级虚拟机」，而是「被隔离的进程」。它们共享宿主机的 Linux 内核，只是通过 Namespace「看」到不同的资源（文件系统、网络、进程树、用户），通过 Cgroup 限制资源使用。

**Namespace 的类型**：

| Namespace | 隔离的资源 | 效果 |
|-----------|-----------|------|
| **PID** | 进程 ID | 容器内看到独立的进程树，PID 1 是容器主进程 |
| **NET** | 网络 | 容器有自己的网络栈（虚拟网卡、路由表、iptables） |
| **MNT** | 文件系统挂载点 | 容器有自己的根文件系统（rootfs） |
| **UTS** | 主机名和域名 | 容器可以有独立的主机名 |
| **IPC** | 进程间通信 | 容器内的信号量、消息队列不互相干扰 |
| **USER** | 用户 ID | 容器内 root 可以映射到宿主机的非 root 用户 |

**Cgroup 控制的资源**：

| 子系统 | 控制内容 | 实际意义 |
|--------|----------|----------|
| **cpu** | CPU 时间分配 | 限制容器最大 CPU 使用率 |
| **memory** | 内存使用上限 | 防止某个容器耗尽内存导致整个系统 OOM |
| **blkio** | 块设备 I/O | 限制磁盘读写带宽 |
| **net_cls** | 网络流量分类 | 配合 tc 做网络 QoS |
| **pids** | 进程数上限 | 防止 fork 炸弹 |

#### 3.1.2 Docker 架构

Docker 不是单一体，而是多个组件的协作：

```
┌─────────────────────────────────────────────────────────┐
│                    Docker Client                         │
│                  (docker 命令行)                          │
└─────────────────────────┬───────────────────────────────┘
                          │ REST API (Unix Socket / TCP)
                          ▼
┌─────────────────────────────────────────────────────────┐
│                   Docker Daemon (dockerd)                │
│                  (守护进程，管理容器)                      │
└─────────┬───────────────┬───────────────┬───────────────┘
          │               │               │
          ▼               ▼               ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ containerd│   │ runc     │    │ containerd│
    │ (容器运行时)│   │ (容器执行器)│   │ (镜像管理) │
    └──────────┘    └──────────┘    └──────────┘
```

**各组件的职责**：
- **Docker Client**：用户敲命令的入口（`docker run`、`docker ps` 等）
- **Docker Daemon**：接收命令，调用 containerd 执行
- **containerd**：管理容器生命周期（启动、停止、暂停），拉取镜像
- **runc**：实际创建和运行容器的底层工具（OCI 规范实现）

**OCI (Open Container Initiative)**：容器格式和运行时的行业标准，确保 Docker 镜像可以在任何 OCI 兼容的运行时上运行（如 containerd、CRI-O、Podman）。

#### 3.1.3 镜像分层与 UnionFS

Docker 镜像不是一个大文件，而是多层文件的叠加。

**镜像层示例**（Ubuntu + Node.js 应用）：

```
┌─────────────────┐
│   可写容器层     │  ← 容器运行时写入的文件（临时）
├─────────────────┤
│  app 代码层      │  ← COPY . /app
├─────────────────┤
│  npm install层   │  ← RUN npm install
├─────────────────┤
│  Node.js 层      │  ← RUN apt install nodejs
├─────────────────┤
│  Ubuntu 基础层   │  ← FROM ubuntu:22.04
└─────────────────┘
```

**UnionFS (联合文件系统)**：
- 多个只读层通过 UnionFS 叠加成一个统一视图
- 上层文件会「覆盖」下层同路径的文件
- 容器启动时在最上层加一个可写层（容器层）
- 修改文件时执行 **CoW (Copy-on-Write)**：从只读层复制文件到可写层，再修改

**镜像层的复用**：相同的基础层可以在多个镜像之间共享。你机器上拉取 10 个基于 `ubuntu:22.04` 的镜像，`ubuntu:22.04` 层只存一份。这解释了为什么 Docker 比虚拟机省空间——共享基础 OS 层。

**Dockerfile 指令与层的关系**：

| 指令 | 是否创建新层 | 说明 |
|------|------------|------|
| `FROM` | ✅ 是 | 引入基础镜像的层 |
| `RUN` | ✅ 是 | 执行命令并提交结果为一个新层 |
| `COPY` / `ADD` | ✅ 是 | 添加文件，创建新层 |
| `ENV` / `ARG` | ❌ 否 | 只是元数据 |
| `EXPOSE` / `CMD` | ❌ 否 | 只是元数据 |

**最佳实践**：把变化频率高的指令（如 `COPY` 源码）放在 Dockerfile 后面，变化少的（如 `RUN apt install`）放在前面。这样修改代码后重建镜像时，只需重建最后一层。

#### 3.1.4 容器网络模式

Docker 提供多种网络模式，决定了容器如何与外界通信。

| 网络模式 | 工作原理 | 容器 IP | 宿主机访问方式 | 适用场景 |
|----------|----------|---------|---------------|----------|
| **bridge（默认）** | 容器连接到 docker0 虚拟网桥，通过 NAT 访问外网 | 172.17.x.x | `-p 宿主机端口:容器端口` | 多个容器互相隔离，需端口映射 |
| **host** | 容器直接使用宿主机网络栈，没有网络隔离 | 无独立 IP | 容器端口直接绑定宿主机 | 追求网络性能，不介意端口冲突 |
| **none** | 无网络 | 无 | 无法访问 | 不需要网络的容器（如离线批处理） |
| **container** | 共享另一个容器的网络栈 | 同另一个容器 | 同另一个容器 | Sidecar 模式（如日志收集） |
| **macvlan** | 为容器分配独立 MAC 地址，直接接入物理网络 | 同网段物理 IP | 直接通过物理 IP 访问 | 需要容器像物理机一样出现在网络中 |

**bridge 模式数据包路径**：
```
容器 (172.17.0.2:2283)
    │
    ▼
veth 虚拟网卡对（容器侧 + 宿主机侧）
    │
    ▼
docker0 网桥 (172.17.0.1)
    │
    ▼ (NAT)
eth0 物理网卡 (192.168.50.175)
    │
    ▼
外部设备 (100.109.179.26)
```

`-p 0.0.0.0:2283:2283` 的含义：监听宿主机所有接口（`0.0.0.0`）的 2283 端口，把流量转发到容器的 2283 端口。

### 3.2 应用部署层（以 Immich 为例）

#### 3.2.1 应用选型：为什么选 Immich

服务器可以跑的服务有很多种（Web 服务器、数据库、缓存、消息队列）。你选择 Immich 作为第一个核心应用，因为它是现代容器化部署的典型案例：

**选型对比**：

| 方案 | 类型 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **Immich** | 开源照片管理 | AI 人脸识别、移动端 App、活跃开发 | 更新频繁（每月 2-3 个 release） | ✅ 选中 |
| **Nextcloud** | 全能云盘 | 功能全（文件、日历、联系人） | 重、慢、PHP 生态 | ❌ 太重 |
| **PhotoPrism** | 照片管理 | AI 强大，Web 体验好 | 无官方移动 App，WebDAV 同步体验差 | ❌ App 缺失 |
| **Piwigo** | 老牌相册 | 稳定、成熟 | 界面老旧，AI 能力弱 | ❌ 缺乏现代感 |

**Immich 的技术特点**：
- 前后端分离：TypeScript 后端 + Flutter 移动端
- 微服务架构：多个服务各司其职
- 容器原生：官方提供完整的 docker-compose.yml

#### 3.2.2 Immich 的微服务组成

Immich 不是一个单一的容器，而是多个容器的协作：

| 服务名 | 镜像 | 职责 | 端口 |
|--------|------|------|------|
| **immich-server** | immich-server | 核心 API、Web 界面、业务逻辑 | 2283 (对外) |
| **immich-machine-learning** | immich-machine-learning | 人脸识别、CLIP 图像特征提取 | 3003 (内部) |
| **database** | postgres:14 | 存储元数据（用户、相册、标签、资产记录） | 5432 (内部) |
| **redis** | redis:7 | 缓存、任务队列（异步任务去重） | 6379 (内部) |
| **typesense** | typesense/typesense | 全文搜索索引 | 8108 (内部) |

**服务间依赖关系**：
```
用户请求 → immich-server (API)
              │
              ├── 读取/写入 → PostgreSQL（元数据）
              ├── 缓存会话 → Redis
              ├── 排队任务 → Redis（Bull 队列）
              ├── 触发 → immich-machine-learning（AI 处理）
              └── 搜索 → Typesense（全文索引）
```

**为什么需要这么多服务**？
- **关注点分离**：AI 模型推理（耗 CPU/GPU）和 API 服务（I/O 密集）分开，可以独立扩展
- **可替换性**：PostgreSQL 可以换成兼容的其他数据库（理论），Redis 可以换成 KeyDB
- **容器化优势**：每个服务可以单独更新、回滚、缩放

#### 3.2.3 Docker Compose 编排

**Docker Compose 是什么**：一个用于定义和运行多容器 Docker 应用的工具。用一个 `docker-compose.yml` 文件配置所有服务，一条命令启动整个栈。

**`docker-compose.yml` 核心结构**：

```yaml
version: "3.8"

services:
  immich-server:                    # 服务名（内部 DNS 可用）
    container_name: immich_server   # 容器名（在宿主机唯一）
    image: ghcr.io/immich-app/immich-server:release  # 镜像来源
    ports:
      - "0.0.0.0:2283:2283"        # 端口映射：宿主机:容器
    volumes:
      - ${UPLOAD_LOCATION}:/usr/src/app/upload  # 挂载上传目录
      - /etc/localtime:/etc/localtime:ro        # 容器时间同步宿主机
    env_file:
      - .env                        # 从 .env 文件读取环境变量
    depends_on:
      - redis                       # 启动顺序依赖（先启动 redis）
      - database
    restart: unless-stopped          # 退出策略：除非手动停止

  redis:
    image: redis:7
    restart: unless-stopped
    # 没有 ports，不对外暴露
```

**`.env` 文件的作用**：存储环境变量，避免敏感信息（数据库密码、API 密钥）写死在 yml 文件中。

```bash
# .env 示例
UPLOAD_LOCATION=/mnt/data/immich/photos
DB_PASSWORD=your_secure_password
```

**Docker Compose 常用命令**：

| 命令 | 作用 | 使用场景 |
|------|------|----------|
| `docker-compose up -d` | 后台启动所有服务 | 首次部署、修改配置后重启 |
| `docker-compose down` | 停止并删除所有容器（保留卷） | 维护、升级 |
| `docker-compose logs -f` | 跟踪所有服务的日志 | 排查启动问题 |
| `docker-compose ps` | 查看服务状态 | 确认所有容器正常运行 |
| `docker-compose exec <服务名> <命令>` | 在容器内执行命令 | 调试、数据库备份 |

#### 3.2.4 首次启动与初始化

启动后的流程：

1. **拉取镜像**：`docker-compose up` 首次执行时，会从 Docker Hub / GHCR 拉取所有服务的镜像
2. **创建网络**：Compose 自动创建一个桥接网络，所有服务加入同一网络
3. **启动依赖**：先启动 `database`、`redis`，等它们健康后再启动 `immich-server`
4. **数据库迁移**：`immich-server` 启动时自动执行数据库 schema 迁移
5. **监听端口**：`immich-server` 开始监听 2283 端口

**首次访问**：浏览器打开 `http://服务器IP:2283`，显示创建管理员账号页面。第一个注册的用户自动成为管理员。

### 3.3 存储与数据持久化层

#### 3.3.1 Volume 挂载类型

容器是无状态的——容器删除后，容器层写入的所有数据都会丢失。数据持久化的方法是用 Volume 把宿主机目录「挂载」进容器。

| 挂载类型 | 语法 | 数据位置 | 适用场景 |
|----------|------|----------|----------|
| **bind mount** | `/host/path:/container/path` | 宿主机任意目录 | 开发环境、需要直接访问文件（如上传目录） |
| **named volume** | `vol_name:/container/path` | `/var/lib/docker/volumes/` | 数据库存储、不需要直接访问 |
| **tmpfs mount** | `--tmpfs /container/path` | 内存 | 临时文件、敏感数据（不落盘） |

**bind mount 的特点**：
- 宿主机路径可以任意指定（如 `/mnt/data/immich/photos`）
- 容器内外都可以直接读写该目录
- 删除容器不会删除数据
- 适合存储「需要被宿主机直接访问」的文件（照片、配置文件）

**你的 Immich 上传目录**：
```yaml
volumes:
  - /mnt/data/immich/photos:/usr/src/app/upload
```

这意味着：手机上传的照片，最终存储在宿主机的 `/mnt/data/immich/photos/`，而不是容器内部。即使删除 Immich 容器重建，照片不丢失。

#### 3.3.2 数据目录规划

**上传目录结构**（Immich 自动创建）：

```
/mnt/data/immich/photos/
├── upload/                # 用户上传的原始文件
│   ├── admin/            # 用户 admin 的资产（按用户分目录）
│   │   ├── 2024/         # 按年
│   │   │   ├── 01/       # 按月
│   │   │   │   └── image1.jpg
│   ├── user2/
├── thumb/                 # 缩略图（AI 生成）
├── encoded/               # 编码后的视频
├── profile/               # 用户头像
└── .immich                # 内部状态文件
```

**数据库卷**（自动创建 named volume）：

```yaml
volumes:
  - pgdata:/var/lib/postgresql/data
```

`pgdata` 是 Docker 管理的 named volume，存储在 `/var/lib/docker/volumes/pgdata`，不要直接修改。

#### 3.3.3 备份策略设计

| 数据类型 | 存储位置 | 备份方法 | 备份频率 |
|----------|----------|----------|----------|
| **照片原图** | `/mnt/data/immich/photos/upload` | rsync 到另一块盘 / 云存储 | 每天增量 |
| **数据库** | PostgreSQL 容器内 | `pg_dump` 导出 SQL | 每天全量 |
| **配置文件** | `/opt/immich/.env`、`docker-compose.yml` | 手动复制 / Git 仓库 | 变更时备份 |

**备份命令示例**：

```bash
# 1. 备份 PostgreSQL 数据库
docker exec immich_postgres pg_dump -U postgres immich > /mnt/data/backups/immich_db_$(date +%Y%m%d).sql

# 2. 备份照片（增量）
rsync -av --delete /mnt/data/immich/photos/upload/ /mnt/backup_disk/photos_backup/

# 3. 备份配置文件
cp /opt/immich/.env /mnt/data/backups/
```

**3-2-1 备份原则**：3 份数据、2 种介质、1 份异地。

### 3.4 配置与调优层

#### 3.4.1 端口绑定：0.0.0.0 vs 127.0.0.1

这是容器网络中最容易踩的坑，值得深入理解。

**`0.0.0.0`**：绑定所有网络接口。
- Tailscale 虚拟网卡（`tailscale0`，IP `100.109.179.26`）
- 物理网卡（`enp3s0`，IP `192.168.50.175`）
- 本地回环（`lo`，IP `127.0.0.1`）

**`127.0.0.1`**：只绑定本地回环接口。流量只能从宿主机本机访问，无法从 Tailscale、局域网、外网进入。

**默认错误的写法**（Immich 官方配置有时如此）：
```yaml
ports:
  - "2283:2283"    # 等价于 0.0.0.0:2283:2283？不对！
```
不写 `0.0.0.0` 时，Docker 默认行为是监听所有接口，但某些 Compose 模板会显式写成 `127.0.0.1:2283:2283`。

**检查方法**：
```bash
netstat -tlnp | grep 2283
# tcp  0  0 0.0.0.0:2283  0.0.0.0:*  LISTEN  -> 正确（Tailscale 可访问）
# tcp  0  0 127.0.0.1:2283  0.0.0.0:*  LISTEN  -> 错误（仅本机）
```

**解决方案**：在 `docker-compose.yml` 中修改：
```yaml
ports:
  - "0.0.0.0:2283:2283"
```

#### 3.4.2 资源限制

**为什么需要资源限制**：容器共享宿主机资源，一个容器可能耗尽所有 CPU 或内存，导致其他服务（包括 SSH）不可用。

**CPU 限制**：
```yaml
services:
  immich-server:
    deploy:
      resources:
        limits:
          cpus: '2'      # 最多使用 2 个 CPU 核心
          memory: 4096M  # 最多使用 4GB 内存
        reservations:
          cpus: '0.5'    # 保证至少 0.5 核
          memory: 1024M  # 保证至少 1GB
```

**OOM（Out of Memory）处理**：容器内存超出限制时，内核的 OOM Killer 会杀死容器进程，导致容器重启。设置 `restart: unless-stopped` 可自动恢复。

#### 3.4.3 自动重启策略

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| `no` | 不自动重启（默认） | 一次性任务 |
| `always` | 任何情况都重启 | 核心服务（数据库、API） |
| `on-failure` | 仅非 0 退出码时重启 | 可能因错误崩溃的任务 |
| `unless-stopped` | 除非手动停止，否则总是重启 | **大部分服务器应用的推荐值** |

`unless-stopped` 的行为：系统启动时自动启动容器（如果之前没手动停止）；容器崩溃时自动重启；手动 `docker stop` 后不再自动启动。

### 3.5 运维监控层

#### 3.5.1 容器生命周期管理

| 命令 | 作用 | 本质 |
|------|------|------|
| `docker run` | 创建并启动新容器 | create + start |
| `docker start` | 启动已存在的容器 | 恢复容器进程 |
| `docker stop` | 优雅停止容器 | 发送 SIGTERM，等待 10 秒后退；未退出则 SIGKILL |
| `docker kill` | 强制停止容器 | 直接发送 SIGKILL，不等待 |
| `docker restart` | 重启容器 | stop + start |
| `docker pause` | 暂停容器内所有进程 | 使用 cgroup freezer，进程挂起但不终止 |
| `docker rm` | 删除容器 | 删除容器元数据和可写层（volume 需额外加 `-v`） |
| `docker prune` | 批量删除未使用的资源 | 清理 `docker system prune` 清理一切未使用的（镜像、容器、网络、build cache） |

**SIGTERM vs SIGKILL**：
- **SIGTERM (15)**：优雅终止信号，进程可以捕捉并执行清理（关闭文件、保存状态）
- **SIGKILL (9)**：暴力终止，内核直接回收进程资源，进程来不及做任何清理
- 生产环境优先用 `stop`（SIGTERM），避免数据损坏

#### 3.5.2 日志查看与追踪

**Docker 日志驱动**：默认 `json-file`，将容器的 stdout/stderr 写入宿主机的 JSON 文件。

```bash
# 查看容器所有日志
docker logs immich_server

# 实时跟踪新日志（类似 tail -f）
docker logs -f immich_server

# 只看最后 100 行
docker logs --tail 100 immich_server

# 带时间戳
docker logs -t immich_server
```

**日志位置**：`/var/lib/docker/containers/<容器ID>/<容器ID>-json.log`

**日志轮转配置**（避免日志占满磁盘）：
```json
// /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

#### 3.5.3 资源使用监控

| 命令 | 显示内容 | 用途 |
|------|----------|------|
| `docker stats` | 所有运行中容器的实时资源（CPU、MEM、NET I/O、BLOCK I/O） | 类似 top，但看容器 |
| `docker stats --no-stream` | 单次采样（不持续刷新） | 获取快照数据 |
| `docker stats <容器名>` | 只查看指定容器 | 针对性监控 |

**输出解读**：
```
CONTAINER ID   NAME            CPU %     MEM USAGE / LIMIT     MEM %     NET I/O
abcd1234       immich-server   15.23%    1.2GB / 3.8GB         31.58%    2.5MB / 1.2MB
```
- **CPU %**：相对于宿主机一个核心的百分比（四核 CPU 最高 400%）
- **MEM USAGE / LIMIT**：当前内存 / 限制（未限制时为宿主机总内存）

## 四、本章核心概念速查表

| 概念 | 一句话解释 | 实际应用 |
|------|-----------|----------|
| **容器** | 被隔离的 Linux 进程 | 封装应用及其依赖，可移植 |
| **Namespace** | 隔离资源的 Linux 内核机制 | PID、NET、MNT 等 8 种隔离类型 |
| **Cgroup** | 限制资源的 Linux 内核机制 | CPU、内存、I/O 上限 |
| **UnionFS** | 叠加多个目录为统一视图 | 镜像分层、CoW、共享基础层 |
| **Docker Compose** | 多容器编排工具 | Immich 的 5 个服务一起管理 |
| **bind mount** | 挂载宿主机目录到容器 | 照片上传目录 `/mnt/data/...` |
| **named volume** | Docker 管理的存储卷 | 数据库数据 `pgdata` |
| **0.0.0.0 vs 127.0.0.1** | 端口监听范围 | 前者允许 Tailscale 访问，后者仅本机 |
| **环境变量** | 容器内配置方式 | `.env` 存储 `UPLOAD_LOCATION` |
| **restart: unless-stopped** | 自动重启策略 | 崩溃后自动恢复 |
| **`docker logs`** | 查看容器输出 | 排查服务启动错误 |
