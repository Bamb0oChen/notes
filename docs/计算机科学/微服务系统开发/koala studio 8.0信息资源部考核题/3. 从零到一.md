前两章讲了很多「一次请求会经过什么」。现在我们反过来做：自己造一条请求，让它从客户端一路走到数据库，再把结果带回来。

这一章先独立完成。目标不是一上来搭一套微服务，也不是把所有技术栈都塞进项目里；我们先把一个小功能做对。只要这条最短路径跑通，第四章的组队开发才有东西可以依靠。

## 3.1 你要做什么

实现一个**报名草稿服务**。用户可以创建一份草稿，查看草稿，修改草稿，最后提交。为了避免接触真实纳新信息，姓名、联系方式等一律使用虚构数据。你可以把它理解成一个缩小很多倍的纳新表单。

一份草稿至少包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定地找到这份草稿，由服务端生成 |
| `nickname` | 虚构称呼，不能为空 |
| `direction` | 想报名的方向，不能为空 |
| `reason` | 一段简短的理由 |
| `status` | `draft` 或 `submitted` |
| `createdAt`、`updatedAt` | 创建和最后修改的时间 |

这里故意没有身份证号、学号和真实手机号。练习数据只要能验证功能就够了。你也可以补充字段，但要说得清它解决什么问题。

## 3.2 先写规则，再写接口

我们约定：创建时状态是 `draft`；草稿可以修改；一旦提交，内容不能再改；同一份草稿重复提交，不能产生第二份记录。你可以选择重复提交返回当前已提交的结果，也可以返回明确的冲突错误，但行为必须固定、写在 README 中，并有测试覆盖。

为什么先写规则？因为 `POST /submit` 这一行代码并不能告诉队友「重复点两次会怎样」。真正难的地方往往是没有说清楚的边界。

建议提供这些接口，路径可按你选择的框架调整，但行为应一致：

| 操作 | 建议接口 | 需要覆盖的情况 |
| --- | --- | --- |
| 创建草稿 | `POST /api/applications` | 正常创建、缺必填项 |
| 查看草稿 | `GET /api/applications/{id}` | 存在、不存在 |
| 修改草稿 | `PUT /api/applications/{id}` | 草稿可改、已提交不可改 |
| 提交草稿 | `POST /api/applications/{id}/submit` | 首次提交、重复提交 |

服务端要校验输入，错误响应要让调用者知道哪里错了。不要把数据库异常堆栈直接返回给用户。接口的具体请求体和响应体，请你自己写在 README 里，并给出至少一组示例。

## 3.3 用什么技术

可以用你已经熟悉的后端语言和框架；这版题不以语言区分成绩。若你想沿着工作室相关的 .NET 路线学习，ASP.NET Core Minimal API 加 SQLite 是一个适合先打通纵向功能的选择。SQLite 便于在本地启动，正式产品如何选数据库是另一道题。

数据库部分先看我在 [CS50 SQL 笔记](../../Harvard%20CS50/python/SQL.md)里留下的 CRUD、查询和 SQLite 操作，再回来想报名草稿有哪些字段、怎样查一条记录。那篇是学习摘记，不是这道题的现成答案；把它用到自己的表上，才算真正走通。

当时我从 CSV 过渡到 SQL，记下了创建、读取、修改和删除这些操作。现在你可以拿它们反查自己的功能：创建草稿对应写入，查看详情对应查询，修改草稿对应更新；提交状态也是一次更新，而且需要额外判断现在是不是还允许更新。光会写一句 SQL，和把业务规则守住，中间还差了这一层。

若选择 .NET，框架操作再查官方的 [ASP.NET Core Minimal API 教程](https://learn.microsoft.com/en-us/aspnet/core/tutorials/min-web-api?view=aspnetcore-10.0) 和 [EF Core SQLite Provider](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/)。先确认本机 SDK 与依赖版本，再照对应版本操作。

前端可以是一个简单页面，也可以先用 HTTP 客户端调用。**必须有服务端和持久化存储**：程序重启后，之前创建的草稿仍应能查到。数据存在内存里的演示可以用来理解接口，但不能算本章完成。

## 3.4 我们按什么顺序做

1. 在 README 里写下字段、状态和四个接口的约定。
2. 先实现创建和查看，确认程序重启后数据还在。
3. 实现修改和提交，明确状态变化。
4. 加输入校验和错误响应。
5. 用正常输入、错误输入、不存在的 ID、重复提交各试一次。
6. 让另一位同学只看 README，在他的环境里启动并复现一条完整路径。

每做完一步，都可以用 Git 留下一次有意义的提交。不需要为了凑提交数把每改一个字都提交一次。

## 3.5 验收时我们会怎么问

给你一份草稿，能不能从创建走到提交？提交后再修改，会发生什么？连续点两次提交，会多出记录吗？程序重启后还能查到吗？如果把必填字段删掉，错误来自浏览器还是服务端？

请准备一段三到五分钟的演示，顺着「请求 → 代码 → 数据库 → 响应」讲。能展示一次你发现并修复的问题，比在幻灯片上列十个技术名词更有说服力。
