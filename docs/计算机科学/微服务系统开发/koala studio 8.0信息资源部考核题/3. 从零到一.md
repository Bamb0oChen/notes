前两章讲了很多「一次请求会经过什么」。现在我们反过来做：自己造一条请求，让它从客户端一路走到数据库，再把结果带回来。

这一章先独立完成。目标不是一上来搭一套微服务；我们先用一个小功能把 .NET、Clean Architecture、领域驱动设计（DDD）和数据存储串起来，弄清业务规则应该住在哪里。只要这条最短路径跑通，第四章的组队开发才有东西可以依靠。

## 3.1 你要做什么

实现一个**报名草稿服务**。用户可以创建一份草稿，查看草稿，修改草稿，最后提交。为了避免接触真实纳新信息，姓名、联系方式等一律使用虚构数据。你可以把它理解成一个缩小很多倍的纳新表单。

一份草稿至少包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定地找到这份草稿，由服务端生成 |
| `nickname` | 虚构称呼，不能为空 |
| `direction` | 想报名的方向，不能为空 |
| `reason` | 一段简短的理由 |
| `status` | `draft` 或 `submitted` |
| `createdAt`、`updatedAt` | 创建和最后修改的时间 |

这里故意没有身份证号、学号和真实手机号。练习数据只要能验证功能就够了。你也可以补充字段，但要说得清它解决什么问题。

## 3.2 规则与接口

我们约定：创建时状态是 `draft`；草稿可以修改；一旦提交，内容不能再改；同一份草稿重复提交，不能产生第二份记录。你可以选择重复提交返回当前已提交的结果，也可以返回明确的冲突错误，但行为必须固定、写在 README 中，并有测试覆盖。

为什么先写规则？因为 `POST /submit` 这一行代码并不能告诉队友「重复点两次会怎样」。真正难的地方往往是没有说清楚的边界。

先用自己的话画出「报名草稿」的状态变化：它刚创建时是什么状态，什么操作能改变内容，提交后又为什么不能修改？图不用复杂，但要标出每次操作允许和不允许的情况。之后写代码时，回头对照这张图检查规则有没有落到实处。

建议提供这些接口，路径可按你选择的框架调整，但行为应一致：

| 操作 | 建议接口 | 需要覆盖的情况 |
| --- | --- | --- |
| 创建草稿 | `POST /api/applications` | 正常创建、缺必填项 |
| 查看草稿 | `GET /api/applications/{id}` | 存在、不存在 |
| 修改草稿 | `PUT /api/applications/{id}` | 草稿可改、已提交不可改 |
| 提交草稿 | `POST /api/applications/{id}/submit` | 首次提交、重复提交 |

服务端要校验输入，错误响应要让调用者知道哪里错了。不要把数据库异常堆栈直接返回给用户。接口的具体请求体和响应体，请你自己写在 README 里，并给出至少一组示例。

## 3.3 领域

DDD 这个名字听起来很大，这一题先只练一件事：**让报名草稿自己守住报名草稿的规则**。我们在题目和代码里尽量说「创建草稿」「修改草稿」「提交草稿」，而不是只说「插入一行」「更新一个状态」。数据库里的 `status` 是存储结果；「已提交的草稿不能再修改」才是我们要表达的业务规则。

可以把一份报名草稿看作一个领域对象：它有稳定的 `id`、内容和状态，对外提供修改、提交这样的行为。修改时由它判断现在是否还是草稿；提交时由它决定重复操作的结果。不要让接口处理函数和数据库更新语句各自再写一套状态判断，否则规则一改，就不知道该改哪一处了。

接着把一次请求拆开看：接口接收输入并返回响应；应用层找到草稿、调用它的行为，再保存结果；领域层决定这次操作是否允许；持久化层负责把对象存进数据库、再读出来。这也是我们在这个小项目里学习 Clean Architecture 的起点：让业务规则不依赖 HTTP 路径和具体数据库。可以在一个项目里用几个文件或目录表达这些职责，**不需要拆成几个服务**。演示时应能指出每条规则实际写在哪里，以及换掉数据库实现时哪些业务代码不需要跟着改。

还有一个边界要分清：`nickname` 为空是输入不合法；已提交后还想修改，是状态不允许；数据库暂时连不上，则是存储故障。它们不应统统变成一句「提交失败」。先把这三种情况在自己的设计里分开，再决定接口怎样告知调用者。

在这道题里，一份报名草稿可以作为聚合根，`id` 用来区分实体，`nickname` 等字段是否值得封装成值对象则要看它们有没有自己的规则。给读取和保存草稿定义一个仓储接口，再用 EF Core 实现它，试着让领域代码不直接调用数据库。请在设计报告里用自己的代码解释「聚合根、实体、值对象、仓储」分别解决什么问题；没有独立规则的字段，不必为了凑术语单独建类。

领域事件也先从真实变化想起：如果草稿提交后要通知别的模块，「草稿已提交」可以是领域事件；真正把消息发到另一个系统时，还要考虑集成事件和失败重试。本章不要求接消息队列，也不要求真的发布事件，但要在报告里说明这两种事件的边界，以及现在为什么暂时不实现。先让模型真的承担规则，再考虑更多抽象是否帮你解决了问题。

## 3.4 用什么技术

这章沿用第二章的 .NET 环境，用 C# 和 ASP.NET Core 实现接口，用 PostgreSQL 保存草稿。工作室日常使用 PostgreSQL 和 EF Core Code First；请为报名草稿建模型、生成迁移，在另一台机器上按 README 创建数据库并跑通。数据库可以用 Docker 启动，但仓库里不要放真实密码或本地数据文件。

数据库部分先看我在 [CS50 SQL 笔记](../../Harvard%20CS50/python/SQL.md)里留下的 CRUD、查询和 SQLite 操作，再回来想报名草稿有哪些字段、怎样查一条记录。那篇是学习摘记，不是 PostgreSQL 教程；把 SQL 的思路用到自己的表上，再学会 EF Core 与 Npgsql 怎样把 C# 对象存进去，才算真正走通。

当时我从 CSV 过渡到 SQL，记下了创建、读取、修改和删除这些操作。现在你可以拿它们反查自己的功能：创建草稿对应写入，查看详情对应查询，修改草稿对应更新；提交状态也是一次更新，但能不能更新，先由报名草稿的规则决定。光会写一句 SQL，和把业务规则守住，中间还差了这一层。

框架操作可以查官方的 [ASP.NET Core Minimal API 教程](https://learn.microsoft.com/en-us/aspnet/core/tutorials/min-web-api?view=aspnetcore-10.0) 和 [Npgsql EF Core 文档](https://www.npgsql.org/efcore/)。先确认本机 SDK 与依赖版本，再照对应版本操作。接口中的请求和响应使用 DTO，别直接把持久化实体原样返回；异步读写数据库时要能解释 `Task`、`await` 和异常怎样沿调用链传播。配置从 `IConfiguration` 读取，日志用 `ILogger` 记录能帮助排查的字段。

前端可以是一个简单页面，也可以先用 `curl` 或 Scalar 调用。**必须有服务端和持久化存储**：程序重启后，之前创建的草稿仍应能查到。数据存在内存里的演示可以用来理解接口，但不能算本章完成。

最后给「查看草稿」加一次 Redis 缓存练习：先从缓存读，没命中再从 PostgreSQL 读并写入缓存；草稿修改或提交后，让下一次查询读到新状态。请记录一次命中、一次未命中和一次更新后的验证结果，并说明如果 Redis 暂时不可用，主业务应该怎样处理。Redis 的 String、Hash、List 各适合存什么可以通过自己的例子说明；这一题只需要用到实际合适的数据结构。分布式锁先理解它想解决哪类并发问题，不要给这份单机草稿服务硬加一把锁。

工作室还有自研的 NOF 框架。请从 [NOF 仓库](https://github.com/XmmShp/NOF) 找一个能看懂的 Web 请求入口，顺着代码或示例看它怎样接收请求、组织业务逻辑，以及和你自己的分层有什么相同与不同。写半页阅读记录即可；这章的系统仍按你自己能解释的方式实现，不要求照搬 NOF。

## 3.5 顺序

1. 在 README 里写下字段、状态、状态变化图和四个接口的约定。
2. 先写报名草稿的创建、修改、提交规则；不接数据库，试试哪些操作应该成功，哪些应该被拒绝。
3. 接上 .NET 接口、EF Core 迁移和 PostgreSQL，确认程序重启后数据还在。
4. 把输入不合法、状态不允许和找不到草稿等情况分别处理清楚。
5. 给查看接口加 Redis 缓存，验证命中、未命中，以及修改后不会读到旧内容。
6. 用正常输入、错误输入、不存在的 ID、重复提交各试一次，并检查实际行为是否符合状态变化图。
7. 让另一位同学只看 README，在他的环境里启动并复现一条完整路径。

每做完一步，都可以用 Git 留下一次有意义的提交。不需要为了凑提交数把每改一个字都提交一次。
