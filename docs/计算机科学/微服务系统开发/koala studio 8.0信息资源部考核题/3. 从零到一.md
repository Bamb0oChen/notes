这一章先独立完成。目标不是一上来搭一套微服务；我们先用一个小功能把 .NET、Clean Architecture、领域驱动设计（DDD）和数据存储串起来，弄清业务规则应该住在哪里。

如果你打开工程，看到一堆文件，不知道先动哪个，先只记住这件事：**跑通别人写好的「创建草稿」，再自己补一条「按 ID 查草稿」。** 创建要跨好几层，所以我们把这一条做成完整示范。

## 3.1 你要做什么

实现一个**报名草稿服务**。用户可以创建一份草稿，查看草稿，修改草稿，最后提交。为了避免接触真实纳新信息，姓名、联系方式等一律使用虚构数据。你可以把它理解成一个缩小很多倍的纳新表单。

一份草稿至少包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定地找到这份草稿，由服务端生成 |
| `nickname` | 虚构称呼，不能为空 |
| `direction` | 想报名的方向，不能为空 |
| `reason` | 一段简短的理由 |
| `status` | `draft` 或 `submitted` |
| `createdAt`、`updatedAt` | 创建和最后修改的时间 |

## 3.2 规则与接口

我们约定：创建时状态是 `draft`；草稿可以修改；一旦提交，内容不能再改；同一份草稿重复提交，不能产生第二份记录。

软件开发的第一步是分析需求，这也是我们为什么一开始要写 PRD 或者 README。拿这份报名草稿来说，我们先弄清楚用户能做什么、什么情况下要拒绝，不用一开始就想数据库怎么写。DDD 也是一样：先把业务规则说清楚，再把需要对外提供的操作写成契约（Contract）。

那么什么是所谓契约呢？上过编程课的同学应该见过函数声明。它先告诉你有这么一个操作、怎么调用，至于操作里面具体怎么做，那是实现要回答的问题。

比如我写了下面这一行

```csharp
Result UpdateUser(UpdateUserRequest request);
```

即使你还没看到函数体，也能知道这里有一个叫 UpdateUser 的操作，它接收一个请求，返回一个结果。契约和这个很像，只不过这次要看懂它的，除了写这段代码的人，还有调用我们服务的其他程序。所以我们还得说清楚：请求里要放什么，成功会得到什么，失败怎么区分；如果通过 HTTP 调用，还要约定用什么方法、发到哪个地址。

不过，写到这里我们可以先问一句：**我们凭什么知道 `UpdateUser` 应该接收这些字段，又应该拒绝哪些请求？**

这些东西不是从函数声明里长出来的。回到开头的报名草稿，我们是先知道「提交以后不能修改」，才知道修改接口需要有一种「这份草稿存在，但现在不能改」的结果。如果这条业务规则还没想清楚，函数签名写得再漂亮，调用方也不知道下一步该怎么做。

所以虽然我们是从契约这个词讲起，真正设计时还是**业务优先**。下面按照我们 Koala 的组织方式，依次看 **Domain、Contract、Application、Infrastructure**。我们就用同一份报名草稿，看看每一块到底写什么。

### 1. Domain：先说清楚，这份草稿能做什么

先把浏览器和数据库都忘掉。假设你手里已经有一份草稿，现在我让你改它的昵称。你首先要问的不是「这是不是一个 PUT 请求」，而是「这份草稿提交了没有」。

这就是领域层要回答的问题。我们先看一个缩小的例子，只保留和这条规则有关的东西：

```csharp
public enum DraftStatus
{
    Draft,
    Submitted
}

public sealed class ApplicationDraft
{
    public DraftStatus Status { get; private set; } = DraftStatus.Draft;

    public void Submit()
    {
        if (Status == DraftStatus.Submitted)
            return;

        Status = DraftStatus.Submitted;
    }
}
```

`private set` 的意思是，外面可以看见它的状态，但不能直接写 `draft.Status = DraftStatus.Submitted`。要提交，就调用 `draft.Submit()`，让草稿自己处理。这里示范的是「重复提交就保持原状态」；你也可以约定重复提交报冲突，但都不能再创建一份草稿。

那么「提交后不能修改」写在哪呢？就写在草稿自己的 `Edit(...)` 里。先不把作业答案贴出来，我们换个场景，看借阅单是怎么阻止「归还后再续借」的：

```csharp
public sealed class BookLoan(DateOnly dueDate)
{
    public DateOnly DueDate { get; private set; } = dueDate;
    public bool IsReturned { get; private set; }

    public void Return() => IsReturned = true;

    public void Renew()
    {
        if (IsReturned)
            throw new InvalidOperationException("已归还的借阅单不能续借。");

        DueDate = DueDate.AddDays(7);
    }
}
```

续借不是直接给 `DueDate` 赋值，而是先调用 `Renew()`，由借阅单判断现在能不能改。用 xUnit 写个最小检查，不启动网站、不连数据库：

```csharp
[Fact]
public void 归还后续借被拒绝且到期日不变()
{
    var dueDate = new DateOnly(2026, 12, 1);
    var loan = new BookLoan(dueDate);
    loan.Return();

    Assert.Throws<InvalidOperationException>(() => loan.Renew());
    Assert.Equal(dueDate, loan.DueDate);
}
```

这里测了两件事：续借被拒绝，而且到期日没被偷偷改掉。回到报名草稿，把「归还」换成「提交」，把「续借」换成「改昵称」，你就知道第一条检查该怎么写了。**一个对象、一个动作、一个可以判断对错的结果，这就是你最先能做的小单元。**

在 Lab3 里，我们可以把 `ApplicationDraft` 当作**聚合根（Aggregate Root）**。先不用把这个词想得太复杂：对这份草稿做业务修改，应该从它提供的行为进去，而不是从外面绕开规则直接改字段。它有自己的 ID，但不必知道 HTTP 是什么，也不必知道最后存的是 PostgreSQL 还是别的数据库。

### 2. Contract：再说清楚，别人怎么使用它

现在我们已经知道什么叫「创建草稿」了，就可以站到调用方那边想：我要给你什么，你会还给我什么？

拿创建来说，用户要填昵称、方向和理由；草稿编号、初始状态和创建时间由服务端决定。也就是说，**请求体不是数据库那一整行的复制品**。下面只摘出创建时用到的请求类型：

```csharp
public sealed record DraftInput(
    string Nickname,
    string Direction,
    string? Reason = null);
```

如果我是前端，我按这样的格式发送：

```http
POST /api/applications HTTP/1.1
Host: localhost:5083
Content-Type: application/json

{
  "nickname": "小松",
  "direction": "后端",
  "reason": "想写一个小服务"
}
```

第一行是方法和路径，`Content-Type` 是请求头，空行下面的 JSON 才是**请求体**。创建成功后返回 `201` 和新草稿的 ID；昵称为空则返回 `400`。下次我要看的不是「所有草稿」，而是刚刚那一份，就把 ID 放进 `GET /api/applications/{id}` 的路径里，不用再发一个 JSON 请求体。

我们 Koala 的 `IUserService` 也是这么回事：接口方法、请求类型、返回类型和公开的路径一起构成了对外的约定。实际项目把这些东西放进 `Koala.Dir.Contract`，所以调用方会引用它，**实现契约的 UserService 自己也会引用它**。

也正因如此，契约里的 `Models.User` 和领域里的 `Domain.User` 虽然都叫 `User`，却不是同一个东西。前者告诉调用方「你能拿到怎样的用户数据」，后者负责「这个用户的资料怎样变化」。

### 3. Application：把一次操作做完

契约说「你可以创建草稿」，领域对象说「一份合法的草稿应该是什么样」。但谁负责先创建，再保存，最后把新 ID 交回去呢？这就是应用层。

我们看 starter 里的创建示范：

```csharp
public async Task<DraftResponse> CreateAsync(
    DraftInput input, CancellationToken cancellationToken)
{
    var draft = ApplicationDraft.Create(
        input.Nickname, input.Direction, input.Reason);

    await _repository.AddAsync(draft, cancellationToken);

    return ToResponse(draft);
}
```

第一步请领域层创建草稿，第二步请仓储保存，第三步把结果整理成对外的响应。`await` 在这里很关键：**保存还没成功，就不能先告诉用户创建好了。**

换成「提交草稿」，流程就是先按 ID 找到草稿，找到后调用 `draft.Submit()`，再保存变化。这里有两个容易混淆的问题：「查不到这份草稿怎么办？」是这次用例要处理的；「这份草稿现在能不能提交？」是草稿自己的业务判断。前者由应用层组织，后者由领域层决定。

所以 `DraftService` 是应用层里负责组织用例的一个类，不是整个报名草稿服务。类似地，我们说 Koala 的 UserService 时，往往是指整个能启动、能接请求的程序；`UpdateUser` 则只是它里面的一个用例处理器。

### 4. Infrastructure：决定这些数据具体怎么存

上面应用层写的是 `_repository.AddAsync(...)`。它只要求「能保存草稿」，没有自己去写 `INSERT`。这个要求可以用一个接口表达：

```csharp
public interface IDraftRepository
{
    Task AddAsync(ApplicationDraft draft, CancellationToken cancellationToken);
}
```

这个接口和 `IUserService` 都是 C# 的 `interface`，但它们约束的不是同一件事。`IUserService` 是**给服务外部用的契约**；`IDraftRepository` 是**应用层给存储实现提出的要求**。它们恰好都用接口表达，不代表都要放进对外的 `Contract` 包。

基础设施层接过这个要求，用 EF Core 和 PostgreSQL 把它实现。只看写入的两行：

```csharp
db.Drafts.Add(draft);
await db.SaveChangesAsync(cancellationToken);
```

第一行把草稿加入 EF Core 的变更跟踪，还没真正往数据库里写；第二行才把变更提交到数据库。以后如果换存储方案，应该主要改这里，而不是回头改「提交后不能修改」那条规则。

### 最后再沿着请求走一遍

前面按的是**设计顺序**：先想业务规则，再把对外契约说清楚，然后安排用例、接上具体技术。程序真的运行起来时，请求当然是先到服务入口：

```text
浏览器 ── HTTP POST ──→ 服务入口：按契约读取请求体
                         → Application：安排创建和保存
                             ├─ Domain：检查规则，创建草稿
                             └─ Infrastructure：通过 EF Core 写入 PostgreSQL
浏览器 ←── HTTP 201 ─── 服务入口：返回新草稿的 ID
```

这里并不是每走一层就发一次 HTTP。浏览器到服务是 HTTP，服务到 PostgreSQL 是数据库连接；中间调用 `ApplicationDraft.Create(...)`、调用仓储，都是同一个进程里的 C# 方法调用。

所以打开 Lab3 starter 后，先别急着把 TODO 挨个填掉。挑一条已经实现的「创建草稿」，追三件事：**表单数据在哪变成 `DraftInput`？草稿初始状态在哪定下来？在哪一行之后，我们才敢告诉用户保存成功？** 看懂这三处，再拿刚创建的 ID 去补「按 ID 查草稿」，你就知道该从哪一块下手了。

所以在开始前不妨先用自己的话画出「报名草稿」的状态变化：它刚创建时是什么状态，什么操作能改变内容，提交后又为什么不能修改？图不用复杂，但要标出每次操作允许和不允许的情况。之后写代码时，回头对照这张图检查规则有没有落到实处。

建议提供这些接口，路径可按你选择的框架调整，但行为应一致：

| 操作 | 建议接口 | 需要覆盖的情况 |
| --- | --- | --- |
| 创建草稿 | `POST /api/applications` | 正常创建、缺必填项 |
| 查看草稿 | `GET /api/applications/{id}` | 存在、不存在 |
| 修改草稿 | `PUT /api/applications/{id}` | 草稿可改、已提交不可改 |
| 提交草稿 | `POST /api/applications/{id}/submit` | 首次提交、重复提交 |

打开 [Lab3 的示范 starter](https://git.koala-studio.org.cn/test-group/lab3/-/tree/docs/lab3-create-example)。按仓库 README 创建个人分支，把 `starter/` 复制到自己的提交目录。后面只改自己的副本。以下命令在包含 `Lab3.slnx` 的目录运行：

```sh

dotnet run --project tests/ArchitectureChecks
```

用 .NET 10。第三条命令不用开网站，也不用开数据库。它会试两件事：正常创建时，草稿有 ID、初始状态正确；昵称只有空格时，创建被拒绝。**第一次练习的最小单元就是这个：一个对象、一个动作、一个能判断对错的结果。** 你不需要先把整套服务搭完，才能知道一条规则写得对不对。

接着准备一个本地 PostgreSQL 数据库，先不用开 Redis。下面这条连接串里的库名、用户名、密码要换成你自己的本地值。设置和启动都在同一个 PowerShell 里运行：

```powershell
$env:ConnectionStrings__PostgreSql = 'Host=localhost;Port=5432;Database=lab3;Username=lab3;Password=换成你的本地密码'
# 已安装兼容的 EF Core 10 工具，就跳过安装这一行。
dotnet tool install --global dotnet-ef --version 10.0.7
dotnet ef database update --project src/Infrastructure --startup-project src/Api
dotnet run --project src/Api -- --urls http://localhost:5083
```

`database update` 在这里是把 starter 已经写好的建表迁移应用到数据库，不是让你先手写一张表。浏览器访问 `http://localhost:5083/health`，看到响应只说明网站起来了。要验创建功能，另开 PowerShell，真正发一条请求：

```powershell
$body = @{ nickname = '小松'; direction = '后端'; reason = '想写一个小服务' } | ConvertTo-Json
$response = Invoke-WebRequest http://localhost:5083/api/applications -Method Post -ContentType 'application/json; charset=utf-8' -Body $body
$response.StatusCode
$response.Content
$id = ($response.Content | ConvertFrom-Json).id
```

预期是 **201**，正文有 `id`，状态是 `draft`。记下这个 ID，等会儿查询要用。把昵称改成空格再试，预期 **400**。如果正常请求返回 **503**，先检查 PostgreSQL 是否在运行、连接串和迁移是否正确；这时不用去改领域类。不要把连接串密码贴进报告。

这时再打开代码。先搜 `MapPost("/api/applications"`，然后沿着方法名往下找：

| 打开哪个文件 | 先找什么 | 它在回答什么问题 |
| --- | --- | --- |
| `Api/Program.cs` | 创建草稿的 POST 路由 | 谁接 HTTP 请求？谁决定返回 201？ |
| `Application/DraftService.cs` | `CreateAsync` | 谁发起创建、等写库完成、把结果转成响应？ |
| `Domain/ApplicationDraft.cs` | `Create` | 谁拒绝空白昵称？谁给草稿设初始状态？ |
| `Infrastructure/DependencyInjection.cs` | `AddAsync` | 哪一行把草稿交给 EF Core？哪一行真正保存？ |

不用一口气读完每个文件。先把这四个方法连起来，再换一个昵称发请求，试着在返回的 JSON 里认出它是从哪一路传下来的。

## 3.4 按 ID 查询

先拿创建时的 ID 发一次 GET：

```powershell
curl.exe -i "http://localhost:5083/api/applications/$id"
```

看到 **501** 是正常的。它不是说「数据库没有这条记录」，是说「模板还没实现查询」。打开基础设施里的 `FindAsync`，你会看到类似这样的一段：

```csharp
public Task<ApplicationDraft?> FindAsync(Guid id, CancellationToken cancellationToken)
    => throw new NotImplementedException("TODO 01: 按 ID 查询；不存在时返回 null。");
```

这段代码的含义是：**给我一个草稿编号，我去数据库找；找到就交回草稿，找不到就交回 `null`。**

- `Guid id` 是传进来的编号，就是上面 POST 拿到的那个 ID。
- `ApplicationDraft?` 是查完以后可能拿到的东西。问号修饰的是**草稿结果**：它可以为 `null`，不是说 ID 可以不传。
- `Task<...>` 表示结果由一个异步操作产生。调用者可以用 `await` 取到最终的草稿或 `null`。`CancellationToken` 则一路交给数据库查询，调用取消时不用自己写一套取消机制。
- `=> throw ...` 是当前整个方法体，一调用就抛出「还没实现」。你要换掉的是这一行，不是方法签名。

如果你写过 SQL，可以先想成「从书表里找一条 `Id` 等于传入编号的记录」。下面是借阅系统里的同类写法，假设 `db.Books` 已经是 EF Core 中的书籍集合：

```csharp
public Task<Book?> FindBookAsync(Guid id, CancellationToken ct)
{
    return db.Books.SingleOrDefaultAsync(book => book.Id == id, ct);
}
```

`book => book.Id == id` 就是在给每条记录问一句：「它的编号是我要找的那个吗？」`SingleOrDefaultAsync` 找到一条就返回，没有就返回 `null`，不止一条会报错；用唯一 ID 查时本来就不应该有两条。这个方法没有写 `async`，是因为它直接把查询返回的 `Task` 交给了调用者。若编辑器找不到这个扩展方法，看看文件有没有引入 `Microsoft.EntityFrameworkCore`。

现在换回作业。先问自己：**书换成了什么对象？要从哪个集合查？哪个比较条件没有变？** 可以从同一个文件里已写好的 `AddAsync` 找集合名。只补这一处，先编译；接下来再做这两处：

1. **应用层 `GetAsync`**：等仓储查完。如果查到了，复用 `CreateAsync` 已经用过的 `ToResponse`；如果没查到，把 `null` 交给上层。别先接 Redis。
2. **API 的 GET 路由**：有响应对象就返回 **200**，没有就返回 **404**。数据库连不上是另一回事，不要吞成 404。

三处接好后，拿刚才保存的 ID 测一次，再换个不存在的 ID 测一次：

```powershell
curl.exe -i "http://localhost:5083/api/applications/$id"
curl.exe -i "http://localhost:5083/api/applications/$([guid]::NewGuid())"
```

应该分别得到 **200 / 404**。然后只重启 API，不清库，用原来的 ID 再查一次。还能查到，才算你自己接通了第一条持久化查询。

## 3.5 接完数据库，再加缓存

这章沿用第二章的 .NET 环境，用 C# 和 ASP.NET Core 实现接口，用 PostgreSQL 保存草稿。工作室日常使用 PostgreSQL 和 EF Core Code First；请为报名草稿建模型、生成迁移，在另一台机器上按 README 创建数据库并跑通。数据库可以用 Docker 启动，但仓库里不要放真实密码或本地数据文件。

框架操作可以查官方的 [ASP.NET Core Minimal API 教程](https://learn.microsoft.com/en-us/aspnet/core/tutorials/min-web-api?view=aspnetcore-10.0) 和 [Npgsql EF Core 文档](https://www.npgsql.org/efcore/)。先确认本机 SDK 与依赖版本，再照对应版本操作。接口中的请求和响应使用 DTO，别直接把持久化实体原样返回；异步读写数据库时要能解释 `Task`、`await` 和异常怎样沿调用链传播。配置从 `IConfiguration` 读取，日志用 `ILogger` 记录能帮助排查的字段。

前端可以是一个简单页面，也可以先用 `curl` 或 Scalar 调用。**必须有服务端和持久化存储**：程序重启后，之前创建的草稿仍应能查到。数据存在内存里的演示可以用来理解接口，但不能算本章完成。

工作室还有自研的 NOF 框架。[NOF 仓库](https://github.com/XmmShp/NOF)作为我们理解「一个请求是怎么进到业务代码里」的例子，值得顺着读一遍。前面在 Lab3 里，我们自己写了 MapPost(...)，告诉 ASP.NET Core：「这个地址收到请求以后，去调用这个方法。」到了 NOF，类似的事情可以通过契约上的 [HttpEndpoint] 声明，再由框架生成路由映射，把请求交给对应的处理器。
