有时候我们把程序写完了，发给队友却收到一句[「我这里跑不起来」](../../MIT%20Missing%20Semester/LECTURE%206%20packaging%20and%20shipping%20code.md)。这不一定是队友的问题：也可能是我们漏写了依赖、把数据库地址留在自己电脑上、忘了提交配置样例。开发的对象不只有编译器，还有之后接手这份代码的人。

这一章过后。我们希望你在出问题时，知道怎么把问题变小，怎么留下可以复现的证据。这次也从工作室实际使用的 .NET 开发环境开始；在第三章中，我们会在这套环境里继续做我们的业务功能。

动手前，我会推荐你先看我整理的 [Missing Semester：Shell](../../MIT%20Missing%20Semester/LECTURE%201-2%20bash%20shell.md) 和 [Git](../../MIT%20Missing%20Semester/LECTURE%205%20git.md)：前者帮你弄清命令在哪里执行、文件在哪里，后者从工作区、暂存区讲到提交和协作。以及[打包与交付代码](../../MIT%20Missing%20Semester/LECTURE%206%20packaging%20and%20shipping%20code.md)和[调试与测试](../../MIT%20Missing%20Semester/LECTURE%204%20debugging%20%26%20profilling.md)

## 2.1 环境

一个能运行的项目至少应说明：.NET SDK 版本、依赖安装方式、启动命令、所需配置和测试命令。这些内容往往会在README.md表示。

注：
```
Windows 同学按工作室规范使用 Visual Studio 2026 Enterprise，Mac 同学可以使用 Rider；其他带 AI 补全的编辑器可以辅助写代码，最终仍要在规范指定的 IDE 中完成编译和调试。
```

环境变量适合放数据库连接、外部服务地址等会随环境变化的配置。注意：密码和令牌不要写死在源码里，也不要提交到仓库。

在开始前，我会推荐你看[这个视频](https://www.bilibili.com/video/BV1aZFDz1ExK/?spm_id_from=333.337.search-card.all.click&vd_source=d29a21e1671c0e8f0a10617e8e3990f6)来了解我们的开发

先用一个很小的 `.NET` Web 项目练习这件事：`GET /health` 返回状态，状态里可以带上当前环境名，但不要泄露连接串或密钥。把这个值放进配置，由 `IConfiguration` 读取；再用依赖注入把负责生成状态的服务交给接口调用。试着用 `ILogger` 记录一次请求，比较日志和接口响应各自该写什么。C# 的类、接口、异常和 `async`/`await` 不用一次学完，先弄懂自己在这个项目里真正用到的部分，尤其别把异步方法写成无法等待的 `async void`。

工作室的日常开发规范还规定了编码、命名和文件布局。项目里放一份 `.editorconfig`，提交前运行 `dotnet format`，再看一眼差异是否只改了你想改的内容。命名要让别人读懂，公共接口写清楚用途；不要把格式化命令当成替自己判断设计是否合理的工具。

## 2.2 Git

必修：[git](../../MIT%20Missing%20Semester/LECTURE%205%20git.md)

Git 可以记录谁在什么时候改了什么，也能让几个人在各自分支上开发。

所以在一个正常的开发流程中，你会需要做：
```text
查看状态 → 选择要提交的文件 → 写清楚一次改动 → 推送 → 让队友检查
```

一次提交最好回答一个问题，例如「增加报名输入校验」或「修复重复提交产生两条记录」。合并代码前看一眼差异，尤其注意 `.env`、数据库文件、构建产物和大体积依赖是否被意外提交。团队协作时，先约定接口字段和返回结果，再分别开发。

btw，工作室使用 `main`、`develop`、`feature/*` 和 `bugfix/*` 这套分支约定，提交信息采用 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)。

## 2.4 测试

页面调试做完，不妨从头再走一次：点击按钮后是否每次都得到相同的文本？解码后的地址为什么打不开？删去多余字符后，浏览器实际请求了什么地址、收到了什么状态码？第二段密文能否用同一个口令还原成可读的文字？不要只留最后的答案，也要留下每一步能被别人重复的证据。

先学会用浏览器开发者工具：在 Elements 里看按钮和页面内容，在 Console 里试解码，在 Network 里核对请求地址、状态码和响应。可以再用 `curl` 验证网页确实能取到，但不要把控制台里跑通一次当作全部测试。把「我以为浏览器做了什么」和「工具里实际看到什么」对起来，才算完成这次调试。

## 2.5 权限与数据边界

进入工作室 GitLab 时，请用自己的考拉工作室 SSO 登录。看清你能访问哪个组、哪个仓库、能不能创建分支；如果遇到无权限，记下页面提示和你已经做过的操作，再联系管理员处理。不要借别人的账号完成验收，也不要把密码、令牌或含有敏感信息的截图放进报告。

页面上的线索只是一道练习，里面的口令不是工作室系统的真实密码。请分清练习用的文本和 SSO 身份凭据；调试浏览器时尤其留意地址栏、Network 和 Console 截图里有没有不该公开的信息。
