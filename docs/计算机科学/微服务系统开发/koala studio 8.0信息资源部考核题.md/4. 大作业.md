前面我们独立做了一份报名草稿。现在把视角拉远一点：报名的人想知道自己有没有交上去，负责审核的人想知道还有多少份没处理，后来接手代码的人则希望能在另一台电脑上把系统跑起来。

**Lab 4 DDL：2027 年 2 月 18 日 23:59（北京时间）。** 考核从 2026 年 10 月 1 日开始；完整时间轴见[前言](./0.%20前言.md)。

这就是本次大作业：**做一个小型的报名与审核系统**。题目借用了纳新的场景，但它是一份练习作品，不接入正式纳新系统，也不使用真实报名资料。

## 4.1 组队与范围

每队不多于三人。可以一人完成，但不要为了凑人数临时拉人挂名。组队后的第一件事不是分前端后端，而是一起约定数据字段、状态流转和接口；否则最后很容易做出两个各自能跑、合在一起就报错的半成品。

系统有两类使用者：

- **报名者**：创建、修改、提交自己的报名；查看自己的状态。
- **审核者**：查看已提交的报名，记录审核意见，把报名标记为通过或未通过。

可以做得朴素，页面不需要炫技。但从浏览器或客户端发出的操作，必须经过服务端规则检查并写入持久化存储。

## 4.2 最低功能

建议使用下面的状态流转：

```text
draft → submitted → approved
                  ↘ rejected
```

其中 `draft` 是草稿，`submitted` 是已提交，`approved` 和 `rejected` 是审核结果。状态只能按你文档里明确的规则变化；例如草稿不能直接变成通过，已审核的报名不能偷偷回到草稿。

最低功能清单：

1. 报名者可以创建、修改、提交并查看自己的报名。
2. 审核者可以查看待审核列表、打开详情、填写意见并作出审核决定。
3. 服务端能区分报名者和审核者，并阻止越权操作。演示可以使用**虚构账号和服务端预置的身份**；要写清身份怎样被服务端确认，以及这种演示方案有什么局限。不能只在前端隐藏按钮，也不能让请求体里的 `role` 字段决定调用者的权限。
4. 数据能持久化。重启服务后，报名和审核结果还在。
5. 关键边界有明确结果：空字段、找不到记录、重复提交、重复审核、报名者尝试审核、审核者访问不该看到的数据。
6. 界面或 API 能让人看见操作结果和错误原因，而不是无论成功失败都显示「操作完成」。

不用为了「微服务」三个字把一个小项目强行拆成五个服务。如果你选择拆分，请解释服务之间的数据怎么流动、失败怎么处理；如果选择一个服务，也请说清它的模块边界。我们的目标是看你理解系统，不是看容器数量。

权限这部分可以先回头看我写的 [OAuth 和鉴权](../../Cursh%20Course%20CS/oauth和鉴权.md)，先分清身份、令牌和权限各自在干什么。本题不要求你照着笔记接入第三方登录；重点是服务端能否守住「报名者」和「审核者」的边界。若你打算把项目放进容器，再参考[服务器软件工作流搭建](../../服务器搭建与运维/4.%20服务器软件工作流搭建.md)里的配置、持久化和日志部分；容器不是最低要求，别为了部署把业务功能耽误了。

我在服务器软件那篇里把路线写成「容器运行时 → 多容器编排 → 存储持久化 → 应用配置 → 数据备份 → 日常运维」。如果你选择做部署扩展，至少沿这条线检查一遍：重建容器后数据还在不在？配置换一台机器能不能重新填？出了错要去哪里找日志？这些问题比「我写了一个 Dockerfile」更接近交付。

## 4.3 自选扩展

最低功能稳了以后，可以选**一项**扩展，并说清它带来了什么问题：

- 审核日志：谁在什么时候做了什么决定，能否追溯？
- 通知：审核结果变化时产生通知；发送失败或重复发送如何处理？
- 附件：上传文件后，谁能下载？怎样限制大小与类型？
- 统计：按状态汇总数量，统计结果和实际数据是否一致？

扩展不是必做项，也不应代替最低功能。选择自己真正有时间验证的一项；做了一堆按钮但边界全是空的，会比只做一个扎实功能更难解释。

## 4.4 中期验收

**中期验收 DDL：2026 年 12 月 10 日 23:59（北京时间）。** 这天也是 Lab 3 的 DDL。中期验收不是要求你提前交出一个完整的大作业，我们主要想知道：独立的小功能是不是真的跑通了，接下来组队要做什么，眼下卡在什么地方。提交入口等工作室通知。

中期提交一份简短报告，附上可以核对的材料：

1. **已完成**：第三章的报名草稿服务运行到哪一步，给出仓库地址、启动方式和一条从创建到提交的实际请求记录。
2. **验证**：至少展示一次正常路径和一次失败路径。不要只写「测试通过」，让我们能看到输入、预期和实际结果。
3. **大作业方案**：小队成员与分工、准备实现的状态流转、接口和数据表草图。尚未组队的同学说明自己的计划和待协调事项。
4. **问题与下一步**：当前最影响进度的一个问题，你已经尝试了什么，以及接下来准备怎样验证或解决。

验收时每个人都要能讲清自己做过的部分。报告可以写得简短，不需要拿一份华丽的 PPT 遮住尚未跑通的程序。中期反馈用于调整后半程计划；最终验收仍按下面的完整交付物进行。

## 4.5 最终要交什么

- **源码**：团队共同维护的仓库或代码包，注明各人完成的部分。
- **README**：环境要求、配置样例、启动命令、测试命令、演示账号或虚构数据准备方法。
- **需求与设计**：一页左右说明状态流转、数据结构、接口和权限边界；图可以简单，关键是和代码一致。
- **验证证据**：至少覆盖一条正常业务路径和 4.2 中的关键异常路径。可以提交测试脚本、自动化测试结果或可复现的请求记录。
- **协作记录**：有意义的提交记录、一次代码互查，以及每个人遇到并解决过的一个问题。
- **演示**：从创建报名到审核结果展示，现场启动或提供可复现的本地演示步骤。

如果某项功能未完成，直接写在 README 的「已知问题」里，说明影响和你已经尝试过的办法。未完成并不值得藏起来；把问题说清楚，至少说明你知道系统现在能做到哪一步。

写最终报告时可以借用我在 [Missing Semester：代码质量](../../MIT%20Missing%20Semester/LECTURE%207%20code%20quailty.md) 里整理的思路：格式、静态检查、测试和交付分别证明什么。不要只贴一张「通过」截图；说明你测的是哪条业务路径，失败时又怎么定位。

## 4.6 我们怎样看作品

第一版暂不设定正式分值和等级线，具体评分以工作室通知为准。评审会重点看：

| 维度 | 会观察什么 |
| --- | --- |
| 功能闭环 | 正常报名和审核能否走通，结果是否落库 |
| 边界与安全 | 非法输入、重复操作、越权操作是否被服务端拦住 |
| 可复现性 | 别人能否按 README 启动、测试、看到同样的结果 |
| 协作 | 分工是否真实，接口是否统一，改动是否有记录 |
| 理解 | 每位成员能否解释自己负责的实现及其与整体的关系 |

答辩时我们可能顺着一条真实的测试请求追问：「如果这里写库成功、后面一步失败，会怎样？」「如果两个人同时审核同一份报名，最后状态是什么？」不要求你一开始就把所有并发问题做到生产级，但需要知道自己的方案在什么情况下可能失效，并能提出验证办法。

最后提醒一句：作品能运行只是起点。你们为什么这样设计、出现错误时怎么定位、换个人接手能否继续开发，这些才是我们希望通过考核看见的东西。
