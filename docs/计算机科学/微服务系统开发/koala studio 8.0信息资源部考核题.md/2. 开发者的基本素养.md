有时候我们把程序写完了，发给队友却收到一句「我这里跑不起来」。这不一定是队友的问题：也可能是我们漏写了依赖、把数据库地址留在自己电脑上、忘了提交配置样例。开发的对象不只有编译器，还有之后接手这份代码的人。

这一章不考大家背多少命令。我们希望你在出问题时，知道怎么把问题变小，怎么留下可以复现的证据。

## 2.1 先把环境说清楚

一个能运行的项目至少应说明：运行时或语言版本、依赖安装方式、启动命令、所需配置和测试命令。README 不需要写成说明书，但要让没有参与你开发的人按步骤跑起来。

我在[打包与交付代码](../../MIT%20Missing%20Semester/LECTURE%206%20packaging%20and%20shipping%20code.md)里先问了一个很实际的问题：「为什么代码在我的电脑上能跑，但在别人的电脑上不行？」所以这次不是让你把 README 当形式填满，而是让另一个人真的照着它跑一遍。

```text
这个项目解决什么问题
需要安装什么
如何配置（只给样例，不放真实密钥）
如何启动
如何验证它真的工作了
目前还没解决什么
```

环境变量适合放数据库连接、外部服务地址等会随环境变化的配置。密码和令牌不要写死在源码里，也不要提交到仓库。

## 2.2 Git 是为了让协作有迹可循

Git 的价值不只是「存个备份」。它可以记录谁在什么时候改了什么，让你在改坏后回看，也能让几个人在各自分支上开发。

我在 [Git 笔记](../../MIT%20Missing%20Semester/LECTURE%205%20git.md)里写过：「Git 并不是自动保存软件。你修改文件以后，需要主动选择要记录的内容，再创建一次提交。」因此这里要你留下的不是一堆「最终版」文件，而是能看懂改动过程的提交记录。

```text
查看状态 → 选择要提交的文件 → 写清楚一次改动 → 推送 → 让队友检查
```

一次提交最好回答一个问题，例如「增加报名输入校验」或「修复重复提交产生两条记录」。合并代码前看一眼差异，尤其注意 `.env`、数据库文件、构建产物和大体积依赖是否被意外提交。团队协作时，先约定接口字段和返回结果，再分别开发；靠最后一天合并时猜对方的字段名，通常会收到惊喜。

## 2.3 调试：先观察，再猜原因

例如提交接口返回了 `500`，你不妨按顺序看：

1. 请求真的发出了吗？请求体是什么？
2. 服务端日志有没有收到？异常出现在哪一层？
3. 数据库是否连通？记录是否已经写入？
4. 你能否用同一份输入再次复现？

日志应能帮助定位错误，但不要把密码、完整令牌或不必要的个人信息打出来。向队友求助时，带上**预期结果、实际结果、复现步骤、相关日志和你已经试过的办法**。

## 2.4 测试不是等项目写完才开始

第三章的最小功能至少检查四类情况：正常提交、缺少必填字段、查找不存在的记录、重复提交。别只展示那条你已经手动点成功十遍的路径。

测试可以先用 HTTP 客户端手动跑，再逐步写成能重复执行的脚本或自动化测试。关键是每次改动后可以迅速回答「原来能用的功能有没有被我改坏」。如果一个 bug 被你修好了，最好留一个会在旧代码上失败、在新代码上通过的测试或复现步骤。

## 2.5 权限与数据边界

安全不只是「加一个登录页」。至少要弄清：谁能看到数据、谁能修改数据、服务端是否独立判断权限、敏感信息是否会出现在日志和仓库里。测试时使用虚构报名信息，不要拿真实纳新资料做公开演示。

本次考核里的系统是练习作品，默认不接入工作室正式 OA、正式纳新系统或真实用户数据。若未来确实要接入，必须先走工作室正式的权限和上线流程。
