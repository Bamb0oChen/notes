# 键盘 KVM 输入异常排障

记录日期：2026-09-08

## 一、问题定位

这次的问题发生在一把迈从 G98 上。打游戏的时候，按住 WASD 或方向键，角色先走一小步，停顿之后才继续移动；在 B 站看视频，长按方向键又从加速变成了连续跳转。第一感觉是键盘的重复延迟出了问题，后面又开始怀疑驱动，绕了一圈才发现，最开始连「键盘怎么接到电脑上」都没有问完整。

**最终验证的结果：G98 经过 KVM 时长按异常，绕过 KVM 直连电脑后恢复正常。**

这里的结论只到「KVM 所在的连接链路」这一层。还没有证据说明 KVM 硬件损坏，也没有完成内部机制的定位。直连是已经验证有效的临时解决方式，经过 KVM 使用的问题仍待处理。

---

## 二、先把「长按」拆开

这次排障最容易混淆的，是把两种问题都叫作「连按有延迟」。

| 情况 | 实际含义 | 这次应该观察什么 |
|---|---|---|
| 首次重复等待 | 按下后，等一段时间才开始重复输入 | 重复开始之前等了多久 |
| 长按被拆成单击 | 手指没有松开，应用却反复收到按下和松开 | 没松手时是否出现 `keyup` |

在记事本里，先移动一次光标、停一下、再连续移动，本身不足以说明驱动异常。游戏按住方向键的表现也不能直接用记事本的重复等待来解释。实际排查中主观估计的停顿约为半秒到一秒，但没有精确计时，不能把它写成测量结果。

**本次真正异常的，是浏览器收到的按键状态不再持续。** 这也是后面事件日志比主观感受更有用的原因。

---

## 三、排查过程与证据

### 3.1 系统设置：发现可疑项，不代表找到原因

首先检查 Windows 的键盘设置，读到的结果如下：

| 检查项 | 结果 | 后续验证 |
|---|---|---|
| `KeyboardDelay` | `0`，最短档 | 系统实际生效值一致 |
| `KeyboardSpeed` | `31`，最快档 | 系统实际生效值一致 |
| 筛选键 | 开启 | 关闭并确认生效，故障仍在 |

筛选键确实开着，但关掉以后游戏和视频里的异常没有消失。到这里，只能说这项修改没有解决问题，不能因为它看起来可疑，就把它当成原因。

### 3.2 虚拟驱动：走了一段没有形成对照的弯路

电脑里存在 UU 远程的虚拟输入设备，以及飞智虚拟键盘。退出可见的 UU 进程后，进一步确认 UU 服务已经停止，但 `gvinput.sys` 和 `gvinputmf.sys` 仍在运行。

于是尝试禁用虚拟键盘以及 UU 的父设备，系统返回：

```text
无法禁用关键系统设备。
```

这说明禁用没有成功。没有成功停用，就没有「停用前异常、停用后正常」的对照，也就不能据此认定这些驱动导致了故障。

这一阶段的问题在于，排查被「发现了第三方驱动」带偏了。驱动存在只是线索，距离证明因果关系还差一步实验。

过程中还提出过安全模式测试，但没有取得安全模式下的有效结果。当前记录不能以此排除第三方软件，也不应把建议执行的步骤写成已经执行的实验。

### 3.3 浏览器事件：把感觉变成可以观察的输出

在普通网页打开开发者工具，在 Console 中输入：

```javascript
onkeydown=onkeyup=e=>console.log(e.type,e.code,e.repeat)
```

这是一段临时检测代码：输出事件类型、按键代码，以及是否为重复按下。浏览器如果不允许粘贴，可以手动输入这一行。执行后点击网页空白处，让焦点离开控制台，再按住 W 三秒后松开；测试结束刷新页面即可清除。

G98 异常时，日志反复出现下面的组合：

```text
keydown KeyW false
keyup KeyW false
keydown KeyW false
keyup KeyW false
```

**手没有松开，日志却一直出现 `keyup`，而每次 `keydown` 的 `repeat` 都是 `false`。** 浏览器收到的是连续单击，这与游戏移动断续、视频长按变跳转的现象相符。

需要注意，这里观察的是浏览器事件，不是原始 USB 报文。它能确认输入到达应用时已经异常，还不能直接指出异常发生在哪一个设备或驱动里。

### 3.4 换键盘：建立第一个有效对照

换另一把实体键盘，执行同样的长按测试，输出恢复为：

```text
keydown KeyW false
keydown KeyW true
keydown KeyW true
keyup KeyW false
```

实际控制台将连续的重复按下合并显示为 43 次。最后松手才出现 `keyup`，与上一组输出有明确区别。

这说明当前电脑并非对所有键盘都表现异常。不过，替换测试没有完整记录是否使用了同一接口和线缆，因此它只能缩小范围，不能单独排除系统侧针对特定设备的处理。

### 3.5 有线连接，仍然少问了一层

随后确认 G98 使用有线连接，日志仍然异常，同时迈从 Hub 检测不到键盘。真正遗漏的信息直到这时才出现：键盘接在 KVM 上。

```text
异常路径：G98 → KVM → 电脑
恢复路径：G98 → 电脑
```

把 G98 从 KVM 拔下来，直接接到电脑 USB 口后，实际使用恢复正常。

「有线」只说明用了线，没有说明中间经过什么。前面的排查一直把连接理解成直连，后面的驱动推断也就建立在不完整的前提上。

## 四、结论能写到哪一层

| 事实或判断 | 当前状态 |
|---|---|
| G98 长按时，浏览器反复收到按下和松开 | 已由事件日志确认 |
| 换另一把键盘后，重复事件正常 | 已由事件日志确认 |
| G98 绕过 KVM 直连后恢复正常 | 已由实际测试确认 |
| 故障与 KVM 所在连接链路有关 | 受到直连对照支持 |
| KVM 硬件损坏，或某个具体固件机制出错 | 尚未确认 |
| 迈从 Hub 无法识别也是 KVM 导致的 | 尚未取得直连后的识别结果 |
| KVM 完全断电后恢复，或更换 KVM 接口后恢复 | 尚未测试 |

「之前一直正常」并不推翻这次的对照结果。它说明还需要找出变化发生在哪里，但目前没有 KVM 型号、固件变更、接口变化或供电状态的完整记录，不能补出一个听起来合理的故事作为根因。

下一轮如果继续排查，应先记录 KVM 型号和接口，再分别验证完全断电重连、不同 USB 接口的表现。每次只调整一项，仍用相同的按键事件测试比较结果。这些属于后续计划，不是本次已完成的修复。

## 五、这次排障留下的方法

回头看，最应该提前做的事其实很简单：画出完整连接路径，然后绕过中间设备。

```text
确认现象
    ↓
记录连接路径：键盘、接收器、KVM、扩展坞、电脑接口
    ↓
用事件日志区分「等待重复」与「反复松开」
    ↓
替换键盘、绕过中间设备，分别做对照
    ↓
再决定是否进入驱动和系统层排查
```

这次和 AI 一起排查，最大的浪费是过早接受了「肯定是驱动」的解释。后面虽然列出了设备名、驱动名，甚至给出了管理员命令，但那些细节并没有填上最初遗漏的连接信息。

技术报告应该保留这种弯路：操作失败就是失败，没测过就是没测过，直连恢复也只说明当前验证到的范围。否则事后把过程写得一路正确，反而丢掉了这次最值得记住的东西。
