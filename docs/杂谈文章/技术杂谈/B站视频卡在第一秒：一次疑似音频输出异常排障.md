# B 站视频卡在第一秒：一次疑似音频输出异常排障

记录日期：2026-10-13。排查发生于 10 月 12 日，重启恢复后整理。

## 一、先说结果

这次 B 站的视频一直停在开头，播放器显示「正在缓冲，0.00 KB/s」。网页、评论和其他网站都正常，同一主路由下另一台以太网设备也能看视频。排查到后面，我又发现耳机没有声音，但麦克风仍能用。最后重启电脑，故障恢复。

我的第一反应是：会不会声卡出了问题，连带让视频也放不出来？这个判断值得继续查，但不能直接写成「声卡掉驱动导致播放失败」。我们没有捕获到音频设备初始化失败的错误，也没有做只恢复音频、不重启电脑的对照。

**目前确认的结果只有：故障期间媒体请求可以成功，耳机输出同时异常，重启后恢复。音频子系统异常是优先怀疑方向，不是已经证实的根因。**

## 二、当时具体是什么情况

| 观察 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| B 站页面、评论正常，视频卡住 | 故障集中在播放链路 | 所有视频节点都正常 |
| 同一路由另一台有线设备正常 | 主路由整体故障的可能性降低 | 故障电脑的 DNS、路由或过滤一定正常 |
| Chrome、Edge 都异常 | 不像 Chrome 单独的配置问题 | 可以排除共用的 Chromium 和系统组件 |
| 耳机无声，麦克风可用 | 输入与输出表现不同 | 整张声卡正常，或声卡驱动一定丢失 |
| 重启后恢复 | 重置运行状态有效 | 已定位到某个驱动或服务 |

出问题的视频是 `BV1tYpb6XEfV`。最初截图显示 720P，后来的播放器日志显示 480P、HEVC。清晰度变了，并不意味着编码也变了。

## 三、从网络查起，但不要停在网络

### 3.1 能拿到播放地址，不等于能持续播放

先在故障电脑上直接请求视频信息接口和播放地址接口，返回业务码均为 `0`。对获取到的视频、音频资源发起小范围请求，也拿到了 HTTP `206`。

`206` 表示服务器响应了部分内容请求。这证明测试路径可以取得媒体数据，但既不证明整个视频都能下载，也不等于浏览器能够完成解封装、解码和音视频同步。直接请求与浏览器实际播放，还可能选到不同节点。

### 3.2 抓包里，先分清视频和弹幕

使用 Wireshark 的 TShark 在以太网接口做短时抓包，没有保存完整抓包文件，只输出连接元数据。

早期针对测试节点抓取，没有匹配流量。这个结果不能解释成「浏览器根本没有下载」：节点可能已经不同，连接可能被复用，或者复现时间没对上。

同步刷新后，捕获到了实际媒体域名的 DNS 查询；另一些连接的 TLS 主机名是 `broadcast.chat.bilibili.com`。后者是弹幕链路，不能拿它的握手成功来证明视频下载正常。

实际媒体节点上还观察到一个 `8082` 连接的 FIN/RST 关闭过程。另行测试该节点的 `443` 和 `8082`，都能快速建立 TCP 连接。

这里仍不能认定服务器拒绝了播放：TCP 建连成功只到传输层，连接关闭也可能来自播放器切换资源或主动取消请求。没有对应的完整请求时序，不能把一次复位当成根因。

### 3.3 浏览器里的证据更直接

DevTools 的 Network 最初看到的是心跳和日志上报。它们返回 `200` 或业务码 `0`，不代表音视频资源正常；统计请求失败，也不能直接解释播放卡顿。

后来按大小查看，能看到多个 `.m4s` 请求返回 `206`，实际传输了几十到几百 KB。到这里，「视频 CDN 完全不可达」已经不能解释现象。

排查中还出现过疑似 Fake-IP 地址，但没有把它与失败媒体请求对应起来，不能据此归因于代理。系统代理和 PAC 当时均未启用，这也不等于不存在其他层面的分流。

## 四、播放器到底走到了哪一步

接着查看 `chrome://media-internals`。日志中的关键内容如下：

```text
codec: hevc
coded size: 852x480
encryption scheme: Unencrypted
D3DVideoDecoder is using D3D11 backend
Video is supported by D3DVideoDecoder
video_buffering_state: BUFFERING_HAVE_ENOUGH
pipeline_buffering_state: BUFFERING_HAVE_ENOUGH
event: kPlay
event: kPause
event: kWebMediaPlayerDestroyed
pipeline_state: kStopped
```

视频使用 HEVC/H.265，硬件解码器已经被选择；后续视频缓冲与播放管线一度都报告数据足够。这不是「播放器连初始化都没成功」的证据。

日志中还有一条无法选择 `DecryptingVideoDecoder` 的提示。但资源标记为未加密，之后又成功选择了正常视频解码器，不能仅凭这条提示认定解密或解码失败。

约 5.2 秒时播放器被销毁。我们没有确认这个时间点是否发生刷新、切清晰度或其他页面操作，所以它不能直接证明播放器崩溃。截图也没有显示明确的音频输出错误或最终解码错误。

Console 里的红色 `unload` 权限策略提示，调用栈涉及 `reportPerformance`。它与页面卸载及统计逻辑有关，并没有提供本次播放失败的直接证据。不应该为了消除红字就随意修改浏览器设置。

## 五、耳机没声音，是这次更值得重视的线索

后来才补充的现象是：耳机输出没声音，麦克风还能输入。

输入和输出是不同的链路。麦克风可以录音，不能证明耳机输出设备、默认设备选择、音频服务或驱动的输出状态正常。结合媒体已有下载、两个浏览器都异常，这个现象让本机音频子系统成为更有价值的排查方向。

我当时说「视频 WAV 无法解析」，这个说法不准确。我们没有识别到 WAV 文件，也没有得到音频格式解析失败的证据。应把以下几个阶段分开：

```text
资源下载 → 解封装 → 音视频解码 → 音频输出 / 画面呈现
```

更谨慎的假设是：**音频驱动、服务或输出设备的运行状态异常，可能影响播放器继续播放。** 具体卡在其中哪一步，现有日志还不足以确定。

## 六、重启解决了，但没有完成根因定位

10 月 13 日重启电脑后，用户确认恢复使用。重启同时重置了浏览器、设备和系统服务等多个状态，属于有效恢复手段，却不是单变量实验。

因此本次结论应记录为：

> 疑似本机音频子系统运行状态异常，伴随耳机无声与 B 站停播；重启后恢复。尚未证实声卡驱动丢失，也未确认两个症状的因果关系。

## 七、下次复现，不再从头猜一遍

1. 先确认输出设备、静音和音量，执行系统声音测试，记录耳机是否有声。
2. 只切换到另一输出设备，其他条件不变，观察同一个视频是否恢复持续播放。
3. 保留当前播放器的完整日志，重点看音频解码器、输出设备错误、缓冲状态与暂停的时间关系。
4. 记录设备状态、音频服务状态和对应时间的系统事件，不只截图一条看起来可疑的提示。
5. 必要时再做受控的音频服务恢复或驱动处理，逐项观察；不要一口气改网络、换编码、重装驱动。

日志可能包含媒体签名地址或其他信息，分享前要去掉 Cookie、令牌和完整签名 URL。

这次最值得留下的不是「重启就好了」，而是：播放器说正在缓冲，并不自动等于网络有问题；请求成功，也不自动等于能播放。把现象、链路和证据分开，才能避免绕着一个猜测排查半天。
